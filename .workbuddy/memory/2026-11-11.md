## P1 认证模块（commit 15d5a97）

10 个接口，21 条用例（全量 54 通过）。

**一处对方案的主动调整**：发邮箱验证码的顺序。
方案写「先写缓存，再判频率」，改成「先占配额，再写缓存」——
原顺序的副作用是：用户在冷却期再点发送，新验证码会覆盖缓存里的旧码，
但他手上收到的是旧邮件，登录必然失败。对外行为一致（第二次仍 400）。

**关键设计**：
- refresh token 不下发，藏在 access 的 `tid` claim 里；刷新用 `verify_exp=False`
- 图形验证码无论对错都删 key；邮箱验证码只在成功后删（输错一次不用重等一分钟）
- 发信频率限制**只按邮箱**，不按 purpose，否则 4 个 purpose 可绕过 60 秒冷却
- 登出幂等：token 缺失/无效一律返回成功
- `EmailSender` 在 debug 且未配 SMTP 时降级为打日志，release 模式直接 500
- 默认管理员启动时自动创建（幂等）

**踩坑**：
- `(uvicorn &)` 后台启动会在工具调用结束后被回收，必须用 `run_in_background: true`
- TestClient 自带事件循环，测试里不能 `asyncio.run` 读 Redis，改用同步 `redis.Redis`
- HTTP header 只能 ASCII，测试用例里别塞中文

## P4 文章模块（commit 1878c0d）

12 个接口（前台 6 + 后台 6），新增 28 条测试，全量 127 通过。

**N+1 优化（实测数据）**：
- 6 篇文章时，游客列表 **5 条 SQL**、登录 **6 条**，与页大小无关
- 构成：count(1) + 主查询(1，含 like/comment 聚合子查询 LEFT JOIN) +
  作者(1) + 分类(1) + 标签(1) + 点赞状态(登录时才有)
- 热度排序必须引用 join 出来的 `column("like_count")`，
  写成 `scalar_subquery()` 等于把 N+1 换了个地方藏

**三个必须遵守的顺序**：
1. 路由：`/random`、`/stats`、`/transfer` 全部注册在 `/{id}` 之前
2. 删文章：先收集图片 key → 提交事务 → 再删 MinIO 文件
   （反了会出现「文件删了、事务回滚了」）
3. 点赞：不预检查，直接 INSERT + 捕获 IntegrityError

**其他**：
- 草稿控制：非作者非管理员返回 404（不返回 403，避免暴露草稿存在）
- 图片差集同步：正文删掉的图清理；**正文无图时保留旧记录**（Go 刻意行为，
  防止「清空重写」误删图）
- 后台 `tag_id` 是单个，前台 `tag_ids` 是逗号分隔，两个模块不同

## P5 评论 + 关于（commit 58a953f）

9 个接口（评论前台 4 + 后台 3 + 关于 2），新增 22 条测试，全量 149 通过。

**评论的四个关键点**：
- `total` 与列表**口径一致**（都含已删），修掉 Go 版「total=3 渲染 5 条」
- 已删评论 `content` 必须置空，否则接口成了软删数据泄露通道
- 一级 DESC / 二级 ASC（方向相反）；分页上限 50 / 30 / 后台 50
- 删一级评论用一条 UPDATE 级联软删（`id = ? OR parent_id = ?`）

**关于页**：
- `git_hub` 保留历史拼写；更新路径是 `PUT /about` 不是 `/admin/about`
- 空表时 6 个文字字段返回 `""`；连管理员都没有才 404
- 表为空时 PUT 会先自动建首条记录

**踩坑**：
- **MissingGreenlet**：评论 `flush` 后 `created_at` 由数据库 DEFAULT 生成，
  Python 侧没值；`_to_item()` 是同步方法，访问它会触发隐式 SELECT → 抛异常。
  修法：`insert` 后 `await session.refresh(comment)` 再 commit。
  凡是「插入后立刻要返回带时间戳的对象」都可能踩这个。
